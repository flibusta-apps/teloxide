# Telegram Bot API 10.1 Support Design

**Status:** Approved with changes by `@oracle` design gate (Gate 0). This
revision incorporates all required changes (B1–B14) and answers from that
review. See `.slim/deepwork/tba-10.1.md` for the full gate transcript
reference.

## Goal

Raise teloxide support from Telegram Bot API 10.0 to **10.1** (announced June
11, 2026), covering every type, field, and method introduced in that release.
Changes from Bot API 10.2 onward are explicitly out of scope.

## Source of truth

Two reference documents, extracted from an archive.org snapshot dated June
13, 2026 (2 days after the 10.1 release, predating the 10.2 release on July
14, 2026), are the field-level source of truth for this work:

- `docs/superpowers/specs/2026-08-26-tba-10.1-reference-rich-messages.md`
- `docs/superpowers/specs/2026-08-26-tba-10.1-reference-join-polls.md`

Snapshot URL: https://web.archive.org/web/20260613201709/https://core.telegram.org/bots/api

Implementers must not add anything beyond what these two documents describe.
Trust the per-type field tables over prose summaries when they conflict (the
reference doc's own "Nested/Recursive Structure Notes" #1 undercounts which
`RichText*` variants have a `text` field — the per-type tables are correct:
every variant except `RichTextAnchor`, `RichTextMathematicalExpression`, and
`RichTextCustomEmoji` has `text`).

## Approach

Follow teloxide's existing API-bump process (`CONTRIBUTING.md`):

1. Maintain Bot API object models manually under `crates/teloxide-core/src/types/`.
2. Maintain method metadata manually in `crates/teloxide-core/schema.ron`.
3. Regenerate request payloads, requester methods, forwarding macros, and
   payload-module exports through the repository's codegen test
   (`crates/teloxide-core/src/payloads/codegen.rs`, run via `cargo test`).
4. Refresh `custom_v2.json` from the corresponding tba-parser schema so type
   consistency checks cover the same API revision.
5. Bump version strings and changelogs per `CONTRIBUTING.md`'s "Bumping
   supported TBA version" checklist.

This preserves the repository's established source-of-truth boundaries:
`schema.ron` covers methods only, Rust type modules cover API objects and
unions.

**Why named structs, not inline enum variants (oracle Q1):** the schema-check
machinery (`crates/teloxide-core/src/codegen/schema_check/`) generates
`check_object(api_schema, schema_for!(X), "X")` for every TG object named in
`custom_v2.json`. A `MessageEntityKind`-style enum with inline struct
variants would not produce a standalone `RichTextBold` type for that
generated check to call `schema_for!` on. So every named TG type in this
release (`RichTextBold`, `RichBlockParagraph`, etc.) **must** be a real
top-level `pub struct`, wrapped by an internally-tagged enum
(`RichTextKind`, `RichBlock`) that does not itself carry a `type` field on
the inner structs — mirroring `InputMedia`/`InputPollMedia`, not
`MessageEntityKind`/`StickerKind`.

## API surface

### 1. Join request queries (small, low risk)

Add fields:
- `User::supports_join_request_queries: Option<bool>`
  (`crates/teloxide-core/src/types/user.rs`)
- `ChatFullInfo::guard_bot: Option<User>`
  (`crates/teloxide-core/src/types/chat_full_info.rs` — common field on the
  outer `ChatFullInfo` struct, not inside `ChatFullInfoKind`)
- `ChatJoinRequest::query_id: Option<String>`
  (`crates/teloxide-core/src/types/chat_join_request.rs`)

Add methods to `schema.ron`, placed near `approveChatJoinRequest` /
`declineChatJoinRequest` (around line 3317):
- `answerChatJoinRequestQuery(chat_join_request_query_id: String, result: RawTy("ChatJoinRequestQueryResult")) -> True`
- `sendChatJoinRequestWebApp(chat_join_request_query_id: String, web_app_url: String) -> True`

**`result` parameter (oracle B14):** model as a small Rust enum
`ChatJoinRequestQueryResult { Approve, Decline, Queue }` with
`#[serde(rename_all = "snake_case")]`, `RawTy("ChatJoinRequestQueryResult")`
in `schema.ron` — mirroring the existing `StickerFormat`-style

also gets `enumeration` validation from the schema checker for free.

### 2. Poll link media (small, low risk)

Add:

- Register `InputMediaLink` as a new `InputPollOptionMedia::Link` variant

  **`input_poll_media.rs`'s `files()`/`files_mut()` exhaustively match every

- `PollMedia::link: Option<Link>` in
  `crates/teloxide-core/src/types/poll_media.rs`, inserted in the existing

No schema.ron changes needed for this area (no new/changed methods).

### 3. Rich messages (large, architecturally significant)

**56 new public types** (25 `RichText*` + `RichText` + 21 `RichBlock*` +
`RichBlock` + 3 supporting sub-objects + `RichMessage` + `InputRichMessage`
+ `InputRichMessageContent` + `Link` + `InputMediaLink`), plus 2 Rust-only
helper types (`RichTextKind`, `MediaRichMessage`), 2 new methods, 1 amended
method applied to **two** generated payloads (`editMessageText` and
`editMessageTextInline`), 1 new `MediaKind` variant, 1 new
`InputMessageContent` variant.

#### RichText type architecture

`RichText` can be a plain `String`, an `Array of RichText`, or one of **25**
named object variants (`RichTextBold` … `RichTextReferenceLink`). Model as:

```rust
// crates/teloxide-core/src/types/rich_text.rs

#[serde(untagged)]
pub enum RichText {
    Plain(String),
    List(Vec<RichText>),
    Formatted(Box<RichTextKind>),
}

#[serde(tag = "type", rename_all = "snake_case")]
pub enum RichTextKind {
    Bold(RichTextBold),
    Italic(RichTextItalic),
    Underline(RichTextUnderline),
    Strikethrough(RichTextStrikethrough),
    Spoiler(RichTextSpoiler),
    DateTime(RichTextDateTime),
    TextMention(RichTextTextMention),
    Subscript(RichTextSubscript),
    Superscript(RichTextSuperscript),
    Marked(RichTextMarked),
    Code(RichTextCode),
    CustomEmoji(RichTextCustomEmoji),
    MathematicalExpression(RichTextMathematicalExpression),
    Url(RichTextUrl),
    EmailAddress(RichTextEmailAddress),
    PhoneNumber(RichTextPhoneNumber),
    BankCardNumber(RichTextBankCardNumber),
    Mention(RichTextMention),
    Hashtag(RichTextHashtag),
    Cashtag(RichTextCashtag),
    BotCommand(RichTextBotCommand),
    Anchor(RichTextAnchor),
    AnchorLink(RichTextAnchorLink),
    Reference(RichTextReference),
    ReferenceLink(RichTextReferenceLink),
}
```

All 25 wire `type` strings match `rename_all = "snake_case"` applied to
these Rust variant names with **zero explicit `#[serde(rename)]` overrides**
needed (verified against the reference spec: `date_time`, `text_mention`,
`custom_emoji`, `mathematical_expression`, `email_address`, `phone_number`,
`bank_card_number`, `bot_command`, `anchor_link`, `reference_link` all fall
out correctly). Do not add per-variant renames speculatively — instead add a
table-driven tag-assertion test (mirroring `poll_media_variants_serialize`
in `input_poll_media.rs:126–143`) that pins all 25 wire strings.

**`Box` placement (oracle B2 — exactly one indirection, not two):** box only
at `RichText::Formatted(Box<RichTextKind>)`. Leaf struct `text` fields are
**unboxed** `RichText` (not `Box<RichText>`):
`RichTextBold { pub text: RichText }`. One `Box` fully breaks the
`RichText → RichTextKind → RichTextBold → RichText` cycle; a second `Box` on
the leaf is redundant, doubles allocations per nesting level, and adds
`Box::new(...)` construction noise across 22 structs. Keeping the box at the
enum arm also bounds `sizeof(RichText)` to roughly the size of a `Box`/`Vec`/
`String` (~32 bytes) regardless of how large `RichTextKind`'s variants get
(e.g. `RichTextTextMention` embeds a whole `User`). Add a `const`-assertion
or `std::mem::size_of` test pinning `RichText` to a small, stable size.

Leaf variants with **no** `text` field: `RichTextAnchor` (`name` only),
`RichTextMathematicalExpression` (`expression` only), `RichTextCustomEmoji`
(`custom_emoji_id` + `alternative_text`). All other 22 variants have an
unboxed `text: RichText` field.

**Gate 1 correction:** `RichTextCustomEmoji.custom_emoji_id` is typed
`CustomEmojiId` (the crate's existing transparent wrapper type), not plain
`String` — matching every other custom-emoji-id site in the codebase
(`sticker.rs`, `reaction_type.rs`, `message_entity.rs`). Wire format is
unchanged (`#[serde(transparent)]`). Also boxed:
`RichTextTextMention.user: Box<User>` (documented in-code; keeps
`RichTextKind`'s largest variant small since every `RichText::Formatted`
node is already a separate heap allocation).

`RichTextDateTime.unix_time: i64` (both `unix_time` and `date_time_format`
are **required**, unlike the similarly-named `MessageEntityKind::DateTime`
fields which are optional) — use `i64`, not `DateTime<Utc>`, matching the
existing `MessageEntityKind::DateTime` convention.

If `clippy::large_enum_variant` fires on `RichTextKind` (plausible now that
leaf `text` fields are unboxed and `RichTextTextMention` embeds `User`),
box the offending inner field (e.g. `RichTextTextMention.user: Box<User>`)
rather than reintroducing a blanket leaf-level `Box<RichText>`.

**Derives (oracle B6/Q6):** `RichText`, `RichTextKind`, and all 25
`RichText*` structs → `Clone, Debug, Eq, Hash, PartialEq, Serialize,
Deserialize` (no `f32`/`f64` fields anywhere in this tree, so full
derivability holds).

#### RichBlock type architecture

`RichBlock` is always an object (never String/Array), one of 21 named
variants:

```rust
// crates/teloxide-core/src/types/rich_block.rs

#[serde(tag = "type", rename_all = "snake_case")]
pub enum RichBlock {
    Paragraph(RichBlockParagraph),
    Heading(RichBlockSectionHeading),      // wire: "heading"
    Pre(RichBlockPreformatted),            // wire: "pre"
    Footer(RichBlockFooter),
    Divider(RichBlockDivider),
    MathematicalExpression(RichBlockMathematicalExpression),
    Anchor(RichBlockAnchor),
    List(RichBlockList),
    Blockquote(RichBlockBlockQuotation),   // wire: "blockquote"
    Pullquote(RichBlockPullQuotation),     // wire: "pullquote"
    Collage(RichBlockCollage),
    Slideshow(RichBlockSlideshow),
    Table(RichBlockTable),
    Details(RichBlockDetails),
    Map(RichBlockMap),
    Animation(RichBlockAnimation),
    Audio(RichBlockAudio),
    Photo(RichBlockPhoto),
    Video(RichBlockVideo),
    VoiceNote(RichBlockVoiceNote),         // wire: "voice_note"
    Thinking(RichBlockThinking),
}
```

As with `RichTextKind`, all 21 wire strings match `rename_all =
"snake_case"` on the Rust variant names chosen above with **zero** explicit
renames needed — pin them with a tag-assertion test instead, do not add
speculative `#[serde(rename)]` attributes.

**Recursion:** `RichBlockList.items: Vec<RichBlockListItem>`,
`RichBlockListItem.blocks: Vec<RichBlock>`,
`RichBlockBlockQuotation.blocks: Vec<RichBlock>`,
`RichBlockCollage.blocks` / `RichBlockSlideshow.blocks: Vec<RichBlock>`,
`RichBlockDetails.blocks: Vec<RichBlock>`,
`RichBlockTable.cells: Vec<Vec<RichBlockTableCell>>`. None of this needs
`Box` — `Vec<T>` is a fixed-size fat pointer regardless of `T`, so
self-containment through a `Vec` field never requires boxing (only direct
single-field self-containment, like `RichText`'s, does).

Supporting sub-objects (no `type` tag, plain structs): `RichBlockCaption`,
`RichBlockTableCell`, `RichBlockListItem`. Put them in `rich_block.rs`
alongside `RichBlock` since they're only referenced from its variants.

**Field-level corrections/additions (oracle B8 — the design's earlier draft
omitted these):**
- `RichBlockTableCell.align: CellAlign` and `.valign: CellVAlign` are
  **required** (non-optional) enumerated strings. Model as small Rust enums
  (`CellAlign { Left, Center, Right }`, `CellVAlign { Top, Middle, Bottom }`,
  `#[serde(rename_all = "snake_case")]`) rather than plain `String` —
  precedent: `StickerFormat`, and enums get schema-checker `enumeration`
  validation that `String` doesn't.
- `RichBlockListItem.type: Option<String>` is a **real data field**
  (ordered-list label style: `"a"`, `"A"`, `"i"`, `"I"`, `"1"` —
  case-sensitive, keep as plain `String`, not an enum, since case carries
  meaning), **not** a serde discriminator. Must be `pub r#type: Option<String>`
  with `#[serde(rename = "type")]`. This field name collision with the
  discriminator concept is a trap: the schema checker's global exception
  `IgnoreFieldName { field_name: "type" }` means a missing/misnamed `type`
  field here will **not** be caught by the automated check — verify it
  manually with a deserialization test asserting `{"type":"a", ...}` round
  trips.
- `RichBlockTable.caption: Option<RichText>` — **not** `RichBlockCaption`.
  This is the one block whose `caption` field diverges from every other
  caption-bearing block (`RichBlockCollage`, `RichBlockSlideshow`,
  `RichBlockMap`, and the 5 media blocks all use `Option<RichBlockCaption>`).
  Double-check this specific field in review.
- `RichBlockMap.location: Location` — import `Location` from the existing
  `crate::types::location` module.
- `RichBlockCaption.text: RichText` is required; `.credit: Option<RichText>`
  is optional. `RichBlockTableCell.text: Option<RichText>` is optional (if
  omitted, the cell is invisible).

**`True`-typed optional flags (oracle B12):** for *received* boolean flags
that are only ever present-as-`true` or absent, follow the codebase's
existing convention (`message.rs:63, 519, 636`) —
`#[serde(default, skip_serializing_if = "std::ops::Not::not")] pub x: bool`
— **not** `Option<bool>`. Applies to: `RichMessage.is_rtl`,
`RichBlockTableCell.is_header`, `RichBlockListItem.has_checkbox` /
`.is_checked`, `RichBlockTable.is_bordered` / `.is_striped`,
`RichBlockDetails.is_open`, and `has_spoiler` on
`RichBlockAnimation`/`RichBlockPhoto`/`RichBlockVideo`. Keep genuine
`Option<bool>` only on the **send-side** `InputRichMessage.is_rtl` /
`.skip_entity_detection` (these mirror `InputMedia*`'s optional-param
semantics, not received-flag semantics).

**Derives (oracle B6/Q6 — `Location` does not derive `Eq`/`Hash`, so
anything transitively containing it can't either):**
- `RichBlock`, `RichBlockMap`, `RichBlockListItem`, `RichBlockList`,
  `RichBlockBlockQuotation`, `RichBlockCollage`, `RichBlockSlideshow`,
  `RichBlockDetails` → `Clone, Debug, PartialEq, Serialize, Deserialize`
  only (no `Eq`/`Hash` — poisoned transitively by `RichBlockMap.location:
  Location`, which itself only derives `Copy, Clone, Debug, PartialEq`
  because of `f64` fields).
- `RichBlockCaption`, `RichBlockTableCell`, `RichBlockParagraph`,
  `RichBlockSectionHeading`, `RichBlockPreformatted`, `RichBlockFooter`,
  `RichBlockDivider`, `RichBlockMathematicalExpression`, `RichBlockAnchor`,
  `RichBlockPullQuotation`, `RichBlockTable`, `RichBlockAnimation`,
  `RichBlockAudio`, `RichBlockPhoto`, `RichBlockVideo`, `RichBlockVoiceNote`,
  `RichBlockThinking` → full `Eq, Hash` derivable (their fields — `RichText`,
  `Animation`, `Audio`, `PhotoSize`, `Video`, `Voice`, ints, bools, enums —
  are all `Eq`/`Hash`-capable). Double check each individually; do not
  blanket-copy the "no Eq/Hash" list onto types that don't actually contain
  `Location`.

`RichBlockThinking` is **send-only** — "may be used only in
`sendRichMessageDraft`; can't be received in messages". Still a normal
`RichBlock` variant with `Deserialize`; add a doc-comment note, no
type-level enforcement is possible or expected (same non-enforcement
approach as `InputRichMessage`'s "exactly one of `html`/`markdown`", below).

Media blocks (`RichBlockAnimation`, `RichBlockAudio`, `RichBlockPhoto`,
`RichBlockVideo`, `RichBlockVoiceNote`) reference existing types `Animation`,
`Audio`, `PhotoSize`, `Video`, `Voice` — already implemented, just import
them.

#### Top-level objects

New file `crates/teloxide-core/src/types/rich_message.rs`:
- `RichMessage { pub blocks: Vec<RichBlock>, pub is_rtl: bool }` (received
  flag — `bool` + `skip_serializing_if`, not `Option<bool>`, per B12 above).
  Derives: no `Eq`/`Hash` (contains `RichBlock`, which is poisoned by
  `Location`).
- `InputRichMessage { pub html: Option<String>, pub markdown: Option<String>, pub is_rtl: Option<bool>, pub skip_entity_detection: Option<bool> }`
  — send-side, genuine `Option<bool>`. **Must derive `Eq, Hash`**
  (`html`/`markdown`/booleans only, no recursion into `RichBlock`) — codegen's
  `eq_hash_suitable` check (`payloads/codegen.rs:217–222`) assumes any
  non-blacklisted `RawTy` param type is `Eq`/`Hash`-capable, and
  `EditMessageText` already derives `Eq, Hash` today, so `InputRichMessage`
  must too or codegen output will be inconsistent.
- `InputRichMessageContent { pub rich_message: InputRichMessage }` — derives
  `Eq, Hash` too (same reasoning).

"Exactly one of `html`/`markdown` must be used" (`InputRichMessage`) is
**not** enforced at the Rust type level — document it in the doc comment,
same non-enforcement approach the codebase already uses for `PollMedia`'s
"at most one of N" and `InputRichMessage`'s TG-mandated flat-struct shape
(an enum would break the schema checker's flat field-presence expectations
for this object).

**`Message` integration (oracle B1 — the earlier draft was wrong and would
have silently dropped message metadata):** do **NOT** add `rich_message` as
a common field on `Message`. `Message` holds only routing/sender metadata;
all content lives in `MessageKind::Common(MessageCommon).media_kind:
MediaKind`, which is `#[serde(untagged)]`, and every existing `MediaKind`
variant requires ≥1 content field to match. A rich message JSON payload
carrying only `rich_message` (no `text`, no `photo`, etc.) would match no
existing `MediaKind` variant and silently fall through to
`MessageKind::Empty {}` — which matches any object — **dropping** all of
`MessageCommon`'s fields (`reply_to_message`, `reply_markup`, `edit_date`,
`business_connection_id`, `forward_origin`, etc.) with no error. Instead:

- Add `MediaKind::RichMessage(MediaRichMessage)` to the existing
  `MediaKind` enum in `message.rs`, placed adjacent to `MediaKind::Text`.
  `MediaRichMessage { pub rich_message: RichMessage }` (Rust-only wrapper
  struct, matching the `MediaText`/`MediaPhoto`/etc. pattern already used
  for every other `MediaKind` variant).
- Add a `Message::rich_message(&self) -> Option<&RichMessage>` accessor next
  to the existing `Message::text()` / `Message::photo()` accessors.
- **Mandatory test:** deserialize a rich message JSON payload that also has
  `reply_to_message` and `reply_markup` set, and assert it lands in
  `MessageKind::Common(MessageCommon { media_kind: MediaKind::RichMessage(..),
  reply_markup: Some(..), .. })` — not `MessageKind::Empty {}`. This is the
  single highest-value regression test in this release.
- Also re-run/extend the existing `MediaKind` deserialization test suite
  after insertion, to confirm the new variant doesn't shadow or get shadowed
  by adjacent variants in the untagged match order (the codebase has prior
  history of `Venue`/`Location` and `Animation`/`Document` ordering hazards
  in this exact enum — see referenced issue in `message.rs` around lines
  472–479).

`InputMessageContent` union (`input_message_content.rs`) is
**`#[serde(untagged)]`**, not tagged. Add the new variant **last** in the
enum (its unique required key is `rich_message`, so it can't collide with
`Text`/`Location`/`Venue`/`Contact`/`Invoice`'s required keys, but ordering
still matters for untagged resolution — append rather than insert in the
middle). Add a round-trip test covering all resulting variants after the
addition.

**Naming (oracle B9):** the codebase renames all five existing TG
`Input*MessageContent` types to `InputMessageContent*` internally
(`InputMessageContentText`, etc.) via `Exception::RenameCheckingObject`
entries in `rust_types_check_codegen.rs`. For consistency, name the new type
`InputMessageContentRichMessage` (not `InputRichMessageContent`, despite
that being the literal TG name) and register the matching rename exception
alongside the other four. This keeps the five `InputMessageContent*`
variants uniformly named.

**This IS a breaking change (oracle B3/Q4 — corrects the earlier draft's
"additive" assumption).** Verified against the actual codegen: `text` is

2. Changes `EditMessageText::new(...)` / `EditMessageTextInline::new(...)`
   arity.
3. Changes the public field `pub text: String` → `pub text: Option<String>`

addition per new method, mirroring the nearest existing entry:
- `crates/teloxide-core/src/bot/api.rs` — the concrete `Requester` impl
- `crates/teloxide-core/src/adaptors/{cache_me,trace,parse_mode}.rs`,
  `crates/teloxide-core/src/adaptors/throttle/requester_impl.rs` — forward-list
  entries
- `crates/teloxide-core/src/adaptors/erased.rs` — trait declaration + impl
  block (this one is more than a one-liner)

## Style conventions for all new structs (apply throughout Phases 1–3)

- `#[serde_with::skip_serializing_none]` **above** `#[derive(...)]` on every
  struct with ≥1 `Option` field (matches `poll_media.rs:10–12`). This
  applies to nearly every new struct except the few with no optional
  fields (`RichTextDateTime`, `RichTextCustomEmoji`, `Link`,
  `InputMediaLink`, `RichBlockDivider`, `RichBlockAnchor`, etc.).
- Doc-comment convention: `/// <one-line description>` + blank `///` +
  `/// [The official docs](https://core.telegram.org/bots/api#<anchor>).`
  — matches `poll_media.rs:7–9`, `input_media.rs:7–9`,
  `message_entity.rs:7–11`. Applies to every new public type, including the
  `RichBlock*` structs in Phase 3a (the earlier plan draft only stated this
  for Phase 2).
- `types.rs` module registration is **two separate alphabetical blocks**:
  a `mod x;` list and a `pub use x::*;` list. Both must be edited for every
  new file (`link.rs`, `rich_text.rs`, `rich_block.rs`, `rich_message.rs`).

## Schema-check machinery (oracle B10 — significant hidden work, budgeted
into Phase 4)

`crates/teloxide-core/src/codegen/schema_check/rust_types_check_tests.rs` is
generated from `custom_v2.json` and asserts every TG object in that schema
has a matching `pub` Rust type reachable via `schema_for!`. Consequences:

- All 56 new public types must exist under exactly their Telegram name
  (already required by the architecture above) for this generated check to
  compile and pass once `custom_v2.json` is refreshed.
- **`RichText`'s mixed `String | Array | Object` union will very likely
  break the schema checker.** `get_type()`
  (`rust_types_check_codegen.rs:202–213`) `unreachable!()`s on `anyOf`
  members that aren't `Null`/`Reference`, and its `oneOf` handling
  (`rust_types_check_codegen.rs:238–255`) panics if variants have differing
  type discriminants — which is exactly what `schema_for!(RichText)`
  produces. Budget for adding
  `Exception::RemoveObjectFromChecking { object: "RichText" }` (and
  possibly `RichBlock` + affected variant structs) to the **hand-maintained**
  exception list in `rust_types_check_codegen.rs`, following the existing
  `ReactionType*`/`ChatMember*` precedent (lines ~1027–1036). If the checker
  panics rather than erroring cleanly, record the panic text — it may
  indicate the checker itself needs a small extension rather than a blanket
  exclusion; raise that as a follow-up rather than silently suppressing
  checking on `RichText` without justification.
- Because of this, **Phase 4 is not purely mechanical** — it can require a
  design decision (which objects to exempt, and why). Keep its oracle gate
  (see phases below), rather than treating it as "mechanical, no gate".

## Delivery phases (for deepwork tracking)

1. **Phase 1 — Foundation** (join request queries + poll link media): new
   fields, `Link`/`InputMediaLink` types (no `type` field — B4),

3. **Phase 3a — RichBlock tree + top-level rich objects (types only)**:
   `rich_block.rs` (21 block variants + 3 supporting sub-objects, including
   the `align`/`valign` enums and the `RichBlockListItem.type` /
   `RichBlockTable.caption` corrections), `rich_message.rs`
   (`RichMessage`/`InputRichMessage`/`InputMessageContentRichMessage`).
   Depends on Phase 2. Deserialization tests only, no `Message`/schema.ron
   integration yet.
4. **Phase 3b — Integration**: `MediaKind::RichMessage` +
   `Message::rich_message()` accessor (B1 — the single highest-risk
   correctness item in this release), `InputMessageContent` union addition
   + rename exception (B9), schema.ron `sendRichMessage`/
   `sendRichMessageDraft`/amended `editMessageText`+`editMessageTextInline`
   (B3 — confirmed BC break), codegen. Depends on Phase 3a. **Oracle gate

   `InputMessageContent`) and the confirmed BC surface.
5. **Phase 4 — Finalization**: `custom_v2.json` regeneration (tba-parser),
   schema-check exception-list updates if `RichText`/`RichBlock` trip the

   changelog entries incl. `[**BC**]` mark + `MIGRATION_GUIDE.md` entry for
   `editMessageText`/`editMessageTextInline`, full `cargo test --features
   "full nightly"` + `cargo clippy` + `cargo fmt --check`. **Oracle gate on
   request only** if `custom_v2.json` regeneration surfaces an unplanned
   exception-list decision or the checker's failure mode is unclear;
   otherwise self-verified against the checklist above.

## Non-goals

- Bot API 10.2 and later changes.
- Rich message Markdown/HTML *parsing/rendering* logic — teloxide only
  models the wire types and request/response shapes; it does not implement
  a Markdown-to-RichText or HTML-to-RichText compiler. `InputRichMessage`
  simply carries `html`/`markdown` as opaque strings, per the API contract
  (Telegram's servers do the parsing).
- Unrelated refactors of message, polling, or dispatching APIs.
- New runtime feature flags, dependencies, or network integration tests.
