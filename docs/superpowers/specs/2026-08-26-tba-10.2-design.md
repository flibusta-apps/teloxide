# Telegram Bot API 10.2 Support Design

**Status:** Approved

## Goal

Raise teloxide support from Telegram Bot API 10.1 to **10.2**, released on
July 14, 2026. The implementation covers every Bot API 10.2 type, field, and
method, while excluding later 10.3 additions.

## Source of truth and boundary

The field-level source of truth is the official Telegram Bot API 10.2
changelog and the official API snapshot from July 19, 2026:

- <https://core.telegram.org/bots/api-changelog#july-14-2026>
- <https://web.archive.org/web/20260719215145/https://core.telegram.org/bots/api>

The implementation must not infer 10.2 details from the current API reference.
In particular, it must exclude 10.3's `EphemeralMessageParameters`, community
join updates, rich-message buttons/documents/expandable block quotations, and
the later ephemeral-message parameter changes.

## Approach

Follow the existing 10.1 support architecture:

1. Model Bot API objects manually under `crates/teloxide-core/src/types/`.
2. Describe method metadata and the API version in
   `crates/teloxide-core/schema.ron`.
3. Regenerate request payloads, `Requester` methods, and payload exports with
   the repository code generator. Generated sources are not hand-edited.
4. Manually add any forwarding entries that generation does not own.
5. Refresh `custom_v2.json` from the matching 10.2 tba-parser schema so the
   Rust/API consistency checks use the same release.

All serializable public models use the crate's established derives, serde
attributes, documentation style, constructors, and builder setters. Conditional
Bot API requirements remain documented rather than being enforced by a new
runtime-validation layer.

## Public API

### Rich-message input

Add send-side support for `InputRichMessage.blocks` and `.media`, plus
`InputRichMessageMedia` and `InputMediaVoiceNote`. Extend the existing
`InputMedia` tagged enum with the voice-note variant.

Add the `InputRichBlock` internally tagged (`type`) union and named structures
for these API object types:

- `InputRichBlockListItem`
- `InputRichBlockParagraph`, `InputRichBlockSectionHeading`,
  `InputRichBlockPreformatted`, `InputRichBlockFooter`,
  `InputRichBlockDivider`, `InputRichBlockMathematicalExpression`, and
  `InputRichBlockAnchor`
- `InputRichBlockList`, `InputRichBlockBlockQuotation`,
  `InputRichBlockPullQuotation`, `InputRichBlockCollage`,
  `InputRichBlockSlideshow`, `InputRichBlockTable`, and
  `InputRichBlockDetails`
- `InputRichBlockMap`, `InputRichBlockAnimation`, `InputRichBlockAudio`,
  `InputRichBlockPhoto`, `InputRichBlockVideo`, `InputRichBlockVoiceNote`, and
  `InputRichBlockThinking`

Use dedicated structs behind the enum, matching `RichBlock` and `InputMedia`.
Recursive block collections use `Vec`; do not introduce unnecessary `Box`
indirection. Fixed discriminator strings are provided by the enum. The list
style `type` remains an ordinary, explicitly renamed data field. Required
fields receive constructors; optional fields receive the existing chainable
setters and omit absent values on serialization.

`InputRichMessage` must document Telegram's one-of constraint: exactly one of
`html`, `markdown`, or `blocks` is required. No custom validation is added.

### Ephemeral messages

Add optional response fields:

- `BotCommand.is_ephemeral`
- `Message.receiver_user` and `Message.ephemeral_message_id`
- `ReplyParameters.ephemeral_message_id`, while changing `message_id` to
  optional because one of these identifiers is required

The `ReplyParameters` invariant is documented on the fields/API type rather
than represented as a breaking tagged abstraction.

Add optional `receiver_user_id: Integer` and `callback_query_id: String`
parameters to these existing request schemas:

`sendMessage`, `sendAnimation`, `sendAudio`, `sendDocument`, `sendLivePhoto`,
`sendPhoto`, `sendSticker`, `sendVideo`, `sendVideoNote`, `sendVoice`,
`sendContact`, `sendLocation`, and `sendVenue`.

Add the following request schemas with their 10.2 archived API signatures and
the same content parameter semantics as their ordinary edit counterparts:

- `editEphemeralMessageText`
- `editEphemeralMessageMedia`
- `editEphemeralMessageCaption`
- `editEphemeralMessageReplyMarkup`
- `deleteEphemeralMessage`

Their archived 10.2 target identifiers are `chat_id` and
`ephemeral_message_id`; use the archived reference, not 10.3's later parameter
shape, when transcribing every parameter and return type into `schema.ron`.
`editEphemeralMessageText` requires `text`; media requires `media`; caption and
reply markup remain optional in their respective edit methods. Do not add the
10.3-only `rich_message`, `receiver_user_id`, new-upload, or
`show_caption_above_media` parameters to these five methods.

### Communities and subscriptions

Add serializable/deserializable models for:

- `Community`
- `CommunityChatAdded`
- `CommunityChatRemoved` (an empty object)
- `BotSubscriptionUpdated`, with `state` as a forward-compatible string enum
  whose known values are `canceled`, `active`, and `failed`

Integrate their optional fields into `Message`, `ChatFullInfo`, and `Update`:
`community_chat_added`, `community_chat_removed`, `community`, and
`subscription`, respectively. These additions must deserialize independently
of older payload shapes.

## Integration and generated layer

Set `ApiVersion` to `10.2` with its release date in `schema.ron`. Run the
existing code generator after schema changes, then update all non-generated
request forwarding surfaces required by compilation, including the concrete
`Bot` requester implementation and the cache, parse-mode, trace, erased, and
throttle adaptors.

Register new type modules and re-exports in `types.rs`. Update schema-check
exceptions only if the 10.2 schema exposes a demonstrable incompatibility with
the checker's representable Rust schema; document the reason and keep the
exception narrowly scoped.

## Documentation and compatibility

Update supported-version notices in both crate roots, both API-coverage badges,
and the root/core changelogs. Update `MIGRATION_GUIDE.md` only if regeneration
reveals a teloxide public API break. The 10.2 changes are otherwise additive;
the Mini App origin hardening is Telegram platform behavior and creates no
Rust API surface.

## Verification

Add focused tests for:

- serialization of every `InputRichBlock` discriminator, nested lists/blocks,
  list-item `type`, and rich-message `blocks`/`media`;
- `InputMediaVoiceNote` and `InputRichMessageMedia` serialization;
- optional ephemeral, community, and subscription fields deserializing into
  their parent models, including an empty `CommunityChatRemoved` object;
- changed `ReplyParameters` serialization for ordinary and ephemeral reply
  identifiers;
- JSON serialization for all five ephemeral request payloads and the amended
  send payloads;
- `BotSubscriptionUpdated` known states and unknown-state behavior.

Run the schema/codegen consistency tests and the project's release verification
command, `cargo test --features "full nightly"`. Generated files must be clean
after the test run. No live Telegram API calls are required.
